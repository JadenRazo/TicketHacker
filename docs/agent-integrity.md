# Agent action integrity and thread context

Draft and summary operations expose read tools only. The dispatcher independently checks the operation's tool set, argument shape and limits, ticket tenant, authorized target, active assignee role and team ownership. Other operations stage permitted writes; a short transaction rechecks current state and related records before applying the whole operation and its receipt. A rejected tool or invalid/incomplete provider completion discards staged changes.

The provider receives the latest customer request even if it does not call `get_ticket`. The shared context loader retains three opening messages, 24 recent messages and the latest inbound text (at most 28 unique messages). It preserves IDs, types, direction, time and evidence labels. It caps the latest request at 8,000 characters and other messages at 1,800, marking truncation and omitted history. Classifiers, direct suggestions/summaries, queued summaries and `get_ticket` use this representation. It is bounded context, not a claim that every historical detail fits or that a model will reason correctly.

`AI_SUGGESTION` is an unsent draft; `NOTE` and `SYSTEM` are internal evidence. Outbound `TEXT` is a recorded reply with unknown delivery unless explicitly confirmed. Widget polling excludes internal messages and drafts. The message listener and queue own widget automation; the widget send handler only persists and emits the customer message. Initial triage uses the first persisted inbound text ID whether it arrives before or after `ticket.created`. OpenClaw no longer emits draft/note creation into the public message event path.

## Operation lifecycle

`AgentOperation` stores tenant, ticket, kind, source, originating inbound message ID (explicitly null when none exists), ticket revision, settings stamp, claim, callback identity and terminal result. Queue IDs are derived from tenant/ticket/kind/origin. Removing a Bull job does not remove its database identity. Completed operations also save `completedTicketVersion` inside the same transaction as their result; dependent replies store `predecessorId`.

Only a `PENDING` operation can claim execution. A duplicate completed request returns the saved result. A running/interrupted claim returns `uncertain`; it is never automatically stolen or replayed. Changed ticket/message state or settings produces `superseded`. Tool writes, message rows and the terminal receipt commit together. Notification emission happens afterward and is best effort. There is no exactly-once notification or delivery guarantee.

When initial triage and reply automation are both enabled, the listener prepares only triage. After its successful `triaged` receipt, the processor prepares the reply with the original inbound message ID. Preparation compares the saved post-triage revision and settings stamp with current state; it records a superseded child if a customer, human or settings change intervened. The normal claim/finish revision checks still apply. Queue retry after commit uses the parent/child receipts. Existing superseded replies, including older sibling replies, are never reset or rebased.

The ticket revision advances on every ticket write and message insertion, edit or deletion through database triggers. Message moves lock both parent tickets in database ID order; merge operations acquire the same locks before moving any messages and reject self-merges or already merged parents. Tenant and ticket locks protect final state validation; assignment locks prevent related-record changes during assignment. Classifier writes use the same state guard and return/report whether their result was actually applied. Existing message updates in Telegram/Discord bookkeeping now acquire the current parent locks before updating message rows. New update/delete consumers must follow this order too; a trigger alone cannot fix a caller that already holds a child row lock.

Manual agent endpoints accept an optional `operationId` for caller retries. Reuse it for the same request; a fresh ID represents a fresh operation. Retries without an explicit origin reuse the saved origin and receipt even after a new customer message. Explicit queue/callback origins and all tenant, target, kind and source changes are still checked. Background operations always require their queued identity; legacy jobs lacking it fail closed and must not be blindly re-enqueued.

Callbacks must first be authorized by an authenticated AGENT via `POST /openclaw/agent/operations/:ticketId`, with `{operationId, kind}`. The response supplies the captured `originMessageId`. The webhook still requires its configured secret and now also requires `operationId`, `eventId`, `kind` and that exact `originMessageId`. It cannot create a new authority record, choose a different target or change operation permissions. A conflicting terminal event ID is rejected. Legacy callbacks without identity are intentionally incompatible.

## Delivery limits and reconciliation

The existing `send_reply` implementation created `AI_SUGGESTION` rows and never used `MessageBusService.queueOutboundMessage`. This change preserves that draft behavior and reports `drafted` / `delivery: not_sent`. It does not activate a new outbound path. The dispatcher refuses terminal ticket status based on an unsent solution. `agent.reply_sent` callbacks are recorded as unverified/uncertain receipts, never as new delivered `TEXT` messages. A callback asserting resolution cannot establish it.

The existing outbound queue has no message/operation receipt that safely reconciles a partial external send. Reusing it blindly would introduce new customer delivery effects and retry ambiguity. A future authorized delivery implementation needs a durable outbox/message identity, adapter acknowledgements and reconciliation for uncertain transport results. Until then a human must send the draft and confirm resolution.

For the existing human outbound path, Telegram/Discord capture pending message IDs before the external send. Acknowledgement bookkeeping locks those messages' current parent tickets in database order and revalidates their locations, so a concurrent merge can safely move them. Only the database acknowledgement is retried (up to three attempts); the send remains outside those transactions. A bookkeeping failure after a channel acknowledgement returns the external ID with `bookkeeping: needs_reconciliation` and logs it rather than throwing it into an automatic send retry. If the database is unavailable, this is not a durable outbox receipt; reconcile the channel acknowledgement. A process crash or ambiguous external-send failure still needs a broader outbox/delivery design.

Dashboard notifications distinguish completed work from `superseded`, `uncertain` and `needs_human` results. Only a `drafted` result inserts text into the reply editor; its notification says that nothing was sent. Both the result panel's Use Reply button and the page callback enforce that action, even when a stopped result retains draft text for review.

After an interrupted operation, inspect its database receipt and persisted ticket/messages. A completed receipt can be returned safely; a `RUNNING` receipt with no result remains uncertain. Do not delete receipts, clear claims or automatically create fresh IDs for the same input. Review the current ticket before explicitly initiating new work. Receipts are not automatically pruned; a retention policy must preserve replay protection.

## Migration and verification

The additive SQL is [20261013000000_agent_integrity/migration.sql](../prisma/migrations/20261013000000_agent_integrity/migration.sql); the consolidated schema SQL contains the same addition. Regenerate Prisma client after adopting the schema. Existing databases created with `db push` need their baseline reconciled before using Prisma Migrate: this first tracked migration is an addition to the existing schema, not a blank-database bootstrap. `db push` alone does not install the revision triggers. The application checks for both enabled triggers and refuses agent writes when they are absent.

No persistent database migration was performed. The addition and its triggers were tested on a minimal schema in disposable PostgreSQL 17.11, including empty `search_path`, opposing merges, mixed merge/channel-bookkeeping races, duplicate claims, post-triage continuation stamps, state changes, rollback and non-owner receipt RLS. The stock test image lacks `vector`, so full consolidated-schema restore remains unverified. The SQL adapter executes the actual transaction bodies and raw queries but does not validate generated Prisma client compatibility. Before deployment, validate a full restore with the required extension, regenerate the client and run the normal API/Jest/dashboard checks with installed dependencies. An unexpected transaction failure must leave the claim uncertain, with no automatic effect replay.

Run the lightweight offline regression suite with `pnpm --filter @tickethacker/api test:agent-integrity`. It is also included before Jest in the API `test` command. It covers combined triage/reply workflows in both event orders and executes the actual panel/page reply controls. It loads the real service/dispatcher/controllers through the installed TypeScript compiler, substitutes framework boundaries, and uses fake providers, effect sinks and a disposable transactional store. It starts no application, database, queue or model. `TICKETHACKER_TYPESCRIPT` may point to an already installed TypeScript module when package links are unavailable. These tests establish application behavior against the fake store, not actual PostgreSQL locking or live provider quality.

The optional PostgreSQL suite is `pnpm --filter @tickethacker/api test:agent-integrity:postgres`. It requires Docker, an **already installed immutable** `TICKETHACKER_TEST_PG_IMAGE=sha256:...`, and installed `pg` (optionally via `TICKETHACKER_TEST_DEPS=/path/to/existing/package`). It never pulls an image. The fixture disables networking, uses a read-only root and a 128 MiB database tmpfs with a 256 MiB memory limit, and removes only its own container/socket directory. The fixture logs resource inspection and cleanup receipts. It creates no persistent database volume and reads no application credentials. Do not point these tests at an existing database.
